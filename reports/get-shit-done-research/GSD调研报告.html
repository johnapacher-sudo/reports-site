Get Shit Done (GSD) 调研报告

一、工具概述

Get Shit Done (GSD) 是一个轻量级但强大的 元提示 (meta-prompting)、上下文工程 (context engineering) 和 规范驱动开发 (spec-driven development) 系统，专为 Claude Code、OpenCode 和 Gemini CLI 设计。

核心理念: "The complexity is in the system, not in your workflow." 复杂性在系统中，而不是在你的工作流中。

解决的核心问题

上下文腐烂 (Context Rot) — 随着 Claude 填满上下文窗口，输出质量会下降。GSD 通过以下方式解决： - 每个 Plan 在全新的上下文窗口中执行 - 保持主会话上下文清洁（30-40%） - 原子任务设计，避免累积垃圾信息

二、安装方式

快速安装

npx get-shit-done-cc@latest

安装时会提示选择： 1. 运行时 — Claude Code / OpenCode / Gemini / 全部 2. 位置 — 全局 (所有项目) 或 本地 (当前项目)

非交互式安装 (Docker/CI)

# Claude Code 全局安装
npx get-shit-done-cc --claude --global   # 安装到 ~/.claude/

# Claude Code 本地安装
npx get-shit-done-cc --claude --local    # 安装到 ./.claude/

# OpenCode 安装
npx get-shit-done-cc --opencode --global # 安装到 ~/.config/opencode/

# Gemini CLI 安装
npx get-shit-done-cc --gemini --global   # 安装到 ~/.gemini/

# 安装到所有运行时
npx get-shit-done-cc --all --global

推荐配置：跳过权限模式

GSD 设计用于无摩擦的自动化，推荐使用：

claude --dangerously-skip-permissions

更新

npx get-shit-done-cc@latest

卸载

# 全局卸载
npx get-shit-done-cc --claude --global --uninstall

# 本地卸载
npx get-shit-done-cc --claude --local --uninstall

三、核心工作流程

GSD 采用 讨论 → 计划 → 执行 → 验证 的循环模式：

┌─────────────────────────────────────────────────────────────────┐
│                      GSD 工作流程                                │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  1. 初始化项目                                                  │
│     /gsd:new-project                                           │
│     ↓                                                          │
│     提问 → 研究 → 需求 → 路线图                                  │
│                                                                 │
│  2. 循环执行每个阶段                                            │
│     ┌─────────────────────────────────────────┐                │
│     │  /gsd:discuss-phase N   捕获实现决策     │                │
│     │           ↓                             │                │
│     │  /gsd:plan-phase N      研究 + 计划     │                │
│     │           ↓                             │                │
│     │  /gsd:execute-phase N   执行所有计划    │                │
│     │           ↓                             │                │
│     │  /gsd:verify-work N     用户验收测试    │                │
│     └─────────────────────────────────────────┘                │
│                                                                 │
│  3. 完成里程碑                                                  │
│     /gsd:complete-milestone                                    │
│     /gsd:new-milestone                                         │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘

详细步骤说明

Step 1: 初始化项目 /gsd:new-project

系统会： 1. 提问 — 询问直到完全理解你的想法（目标、约束、技术偏好、边缘情况） 2. 研究 — 生成并行 Agent 调查领域（可选但推荐） 3. 需求 — 提取 v1、v2 和超出范围的内容 4. 路线图 — 创建映射到需求的阶段

创建的文件: - PROJECT.md — 项目愿景 - REQUIREMENTS.md — 需求文档 - ROADMAP.md — 开发路线图 - STATE.md — 状态和决策 - .planning/research/ — 研究文档

Step 2: 讨论阶段 /gsd:discuss-phase [N]

这是塑造实现的关键步骤

路线图每个阶段只有一两句话，不足以构建你想象的东西。此步骤在研究或计划之前捕获你的偏好：

  • 视觉功能 → 布局、密度、交互、空状态
  • API/CLI → 响应格式、标志、错误处理、详细程度
  • 内容系统 → 结构、语调、深度、流程
  • 组织任务 → 分组标准、命名、重复、异常

创建的文件: {phase}-CONTEXT.md

Step 3: 计划阶段 /gsd:plan-phase [N]

系统会： 1. 研究 — 调查如何实现此阶段，由 CONTEXT.md 决策指导 2. 计划 — 创建 2-3 个具有 XML 结构的原子任务计划 3. 验证 — 检查计划是否满足需求，循环直到通过

每个计划足够小，可以在全新的上下文窗口中执行。

创建的文件: - {phase}-RESEARCH.md - {phase}-{N}-PLAN.md

Step 4: 执行阶段 /gsd:execute-phase <N>

系统会： 1. 分波运行计划 — 尽可能并行，依赖时顺序 2. 每个计划全新上下文 — 200k tokens 纯用于实现 3. 每任务提交 — 每个任务获得自己的原子提交 4. 对照目标验证 — 检查代码库是否实现了阶段的承诺

创建的文件: - {phase}-{N}-SUMMARY.md - {phase}-VERIFICATION.md

Step 5: 验证工作 /gsd:verify-work [N]

这是确认实际工作的步骤

自动验证检查代码是否存在和测试是否通过。但功能是否按预期工作？

系统会： 1. 提取可测试的交付物 — 你现在应该能做什么 2. 逐个引导你 — "你能用邮箱登录吗？" 是/否，或描述问题 3. 自动诊断失败 — 生成调试 Agent 找到根本原因 4. 创建验证修复计划 — 准备立即重新执行

创建的文件: - {phase}-UAT.md - 修复计划（如果发现问题）

Step 6: 完成里程碑

/gsd:discuss-phase 2
/gsd:plan-phase 2
/gsd:execute-phase 2
/gsd:verify-work 2
...
/gsd:complete-milestone
/gsd:new-milestone

五、快速模式 (Quick Mode)

用于不需要完整规划的临时任务

快速模式提供 GSD 保证（原子提交、状态跟踪）和更快的路径：

  • 相同的 Agent — 规划器 + 执行器，相同质量
  • 跳过可选步骤 — 无研究、无计划检查器、无验证器
  • 独立跟踪 — 位于 .planning/quick/，不在阶段中

使用场景: Bug 修复、小功能、配置更改、一次性任务

/gsd:quick
> What do you want to do? "Add dark mode toggle to settings"

创建的文件: - .planning/quick/001-add-dark-mode-toggle/PLAN.md - SUMMARY.md

六、配置选项

GSD 在 .planning/config.json 中存储项目设置。

核心设置

设置 选项 默认值 控制内容
mode yolo, interactive interactive 自动批准 vs 每步确认
depth quick, standard, comprehensive standard 计划彻底性（阶段 × 计划）

模型配置

控制每个 Agent 使用的 Claude 模型，平衡质量与 Token 消耗。

配置文件 规划 执行 验证
quality Opus Opus Sonnet
balanced (默认) Opus Sonnet Sonnet
budget Sonnet Sonnet Haiku

切换配置：

/gsd:set-profile quality

工作流 Agent

这些在计划/执行期间生成额外的 Agent，提高质量但增加 Token 和时间。

设置 默认值 功能
workflow.research true 在计划每个阶段前研究领域
workflow.plan_check true 在执行前验证计划是否实现阶段目标
workflow.verifier true 在执行后确认必须项是否已交付

可覆盖每次调用：

/gsd:plan-phase --skip-research
/gsd:plan-phase --skip-verify

Git 分支策略

设置 选项 默认值 功能
git.branching_strategy none, phase, milestone none 分支创建策略

策略说明： - none — 提交到当前分支（默认 GSD 行为） - phase — 每个阶段创建分支，在阶段完成时合并 - milestone — 整个里程碑创建一个分支，完成时合并

七、为什么 GSD 有效

1. 上下文工程

GSD 为 Claude 提供所需的上下文：

文件 功能
PROJECT.md 项目愿景，始终加载
research/ 生态系统知识（栈、功能、架构、陷阱）
REQUIREMENTS.md 范围内的 v1/v2 需求，带阶段可追溯性
ROADMAP.md 去向，完成什么
STATE.md 决策、阻塞、位置 — 跨会话记忆
PLAN.md 具有 XML 结构的原子任务，验证步骤
SUMMARY.md 发生了什么，改变了什么，提交到历史
todos/ 捕获的想法和后续工作

2. XML 提示格式

每个计划都是为 Claude 优化的结构化 XML：

<task type="auto">
  <name>Create login endpoint</name>
  <files>src/app/api/auth/login/route.ts</files>
  <action>
    Use jose for JWT (not jsonwebtoken - CommonJS issues).
    Validate credentials against users table.
    Return httpOnly cookie on success.
  </action>
  <verify>curl -X POST localhost:3000/api/auth/login returns 200 + Set-Cookie</verify>
  <done>Valid credentials return cookie, invalid return 401</done>
</task>

3. 多 Agent 编排

每个阶段使用相同模式：轻量编排器生成专用 Agent，收集结果，路由到下一步。

阶段 编排器做 Agent 做
研究 协调、呈现发现 4 个并行研究者调查栈、功能、架构、陷阱
计划 验证、管理迭代 规划器创建计划、检查器验证、循环直到通过
执行 分组为波、跟踪进度 执行器并行实现，每个都有全新的 200k 上下文
验证 呈现结果、路由下一步 验证器检查代码库是否满足目标、调试器诊断失败

结果：你可以运行整个阶段 — 深度研究、创建和验证多个计划、跨并行执行器编写数千行代码、自动对照目标验证 — 主上下文窗口保持在 30-40%。

4. 原子 Git 提交

每个任务完成后立即获得自己的提交：

abc123f docs(08-02): complete user registration plan
def456g feat(08-02): add email confirmation flow
hij789k feat(08-02): implement password hashing
lmn012o feat(08-02): create registration endpoint

好处： - Git bisect 找到确切的失败任务 - 每个任务独立可回滚 - 未来会话中 Claude 的清晰历史 - AI 自动化工作流中更好的可观察性

九、适用人群

"People who want to describe what they want and have it built correctly — without pretending they're running a 50-person engineering org."

想要描述他们想要什么并正确构建的人 — 不需要假装运营一个 50 人的工程组织。

适合： - 独立开发者 - 小团队 - 快速原型开发 - 想要可靠 AI 辅助编码的人

不适合： - 需要严格企业流程的团队 - 不使用 Claude Code/OpenCode/Gemini CLI 的人

十二、总结

GSD 的核心价值：

  1. 简单的工作流 — 只需几个命令
  2. 强大的底层系统 — 上下文工程、XML 格式、多 Agent 编排
  3. 解决上下文腐烂 — 每个 Plan 在全新上下文执行
  4. 原子提交 — 清晰的 Git 历史
  5. 灵活配置 — 质量vs成本平衡

Claude Code is powerful. GSD makes it reliable.
